## 4. How order status affects revenue, cost and profit

| scope | rule | orders_checked | violations |
|---|---|---|---|
| All | GMV = sum of line revenue (post-discount) | 30054 | 0 |
| All | Profit = net revenue - total cost | 30054 | 0 |
| All | Order discount = every line discount | 30054 | 0 |
| Completed | Net revenue = GMV + shipping fee (tax excluded) | 28436 | 0 |
| Completed | Total cost = sum of line cost | 28436 | 0 |
| Refunded | Net revenue = 0 | 1253 | 0 |
| Refunded | Total cost = sum of line cost (goods not recovered) | 1253 | 0 |
| Cancelled | Net revenue, cost and profit = 0 | 365 | 0 |

Resulting definitions (see `docs/metric_definitions.md`):
- **GMV** (`gross_merchandise_value_usd`) is the *post-discount* merchandise value of every placed order, whatever its status. It excludes shipping and tax and measures demand, not earned revenue.
- **Net revenue** is recognised only on Completed orders and equals GMV + shipping fee. Sales tax is excluded (it is a pass-through liability).
- **Refunded orders** have zero revenue but keep their merchandise cost, so each one is a loss equal to the cost of goods. The data implies returned goods are not restocked; this is a property of the synthetic data and is treated as an assumption.
- **Cancelled orders** carry zero revenue, cost and profit, even though their line items keep a cost value. Order-level fields are the source of truth.
- Because of these rules, **AOV uses Completed orders only**, and the **refund rate uses fulfilled orders** (Completed + Refunded) as its denominator.
- Joining orders to order_items repeats order-level values once per line. Line-level revenue must be summed from `line_revenue_usd` and order-level values from the orders table; never sum order fields after the join (fan-out).

Findings and resolutions:
- **Window definitions (reverse-engineered and verified):** 12-month features use Completed orders and tickets dated from 2025-05-31 to 2026-05-31 inclusive, and 90-day web features use sessions from 2026-03-02 to 2026-05-31 inclusive. `refund_rate_12m` is refunded orders divided by *all* orders in the window (cancellations included), which differs slightly from the KPI refund rate. `cart_add_rate_90d` is cart adds per product view.
- **Recency sentinel:** for the 606 customers with no Completed order in the 12-month window, `recency_days` is set to `days_since_signup + 30`. Of those, 289 customers did buy earlier, so their real recency is overstated or understated by an arbitrary amount, and 317 never purchased at all. **Resolution:** models use `days_since_last_purchase` (true recency over all observed history) plus explicit `never_purchased` and `no_purchase_12m` flags instead of the sentinel. Notebook 02 checks how sensitive the results are to this change.
- **Imputed values:** customers without tickets have `avg_csat_12m = 4.0` and `avg_resolution_hours_12m = 0` (3,702 customers). `support_tickets_12m = 0` identifies these rows, so models can separate the imputed value from real scores.
- **Target:** `churned_next_90d` describes events after the snapshot. Raw data ends on 2026-05-31, so the label **cannot be verified** from the transactions. The project documentation states that it is synthetic and generated probabilistically from risk signals plus noise, so model scores measure how well the generator's logic is recovered, not real customer behaviour.
- **Static attributes:** `loyalty_tier`, `region`, `acquisition_channel` and `preferred_device` are single current values with no history. If the tier were assigned *after* the snapshot, it would leak information. The project assumes it was known at the snapshot date, and this assumption is documented as a risk.
- **Excluded from predictors:** `customer_id`, `snapshot_date` and the target. This is enforced in code by `features.assert_no_leakage`.

## 8. Assumptions and limitations

- The data is synthetic. Distributions are cleaner and more uniform than real data. For example, funnel conversion barely varies by device or traffic source, so a lack of differences should not be read as a real-world finding.
- Order history begins in January 2024, but 2023 sign-ups exist. Cohort analyses label the first *observed* purchase, so 2024 cohorts mix new and existing customers.
- Profit excludes shipping, payment, support, overhead and marketing costs, none of which are in the data at order level. Marketing spend is analysed separately and only at channel and month grain.
- Organic Search and Referral have recorded spend. This is assumed to cover SEO, content and referral-programme costs.
- Raw CSV files are read-only inputs. No rows were removed or values altered; every correction (e.g. true recency) is a new derived column.
